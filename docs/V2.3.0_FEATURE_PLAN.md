# v2.3.0 Feature Planning & Analysis

**Date**: 2025-11-19
**Version**: v2.3.0 (Planning Phase)
**Status**: PLANNING IN PROGRESS

---

## Executive Summary

This document outlines the comprehensive plan for v2.3.0, the next major release of WebScrape-TUI following the successful v2.2.0 security features release. The focus is on **communication, collaboration, and enhanced security**.

---

## 1. Post-v2.2.0 Analysis

### What We Have (v2.2.0)

**Security Foundation** ✅:
- Password policy with strength validation
- Rate limiting and account lockout
- Comprehensive audit logging
- Password reset tokens (256-bit)
- User quotas (articles/scrapers)
- Enhanced authentication

**Gaps Identified** 🔍:
- ❌ No email/notification system (password reset tokens generated but not sent)
- ❌ No 2FA/MFA implementation
- ❌ Password expiration partially implemented (field exists, not enforced)
- ❌ No real-time security alerts
- ❌ No user collaboration features
- ❌ No article sharing between users
- ❌ No team/organization support
- ❌ Limited audit log analytics

### User Feedback Areas (Predicted)

Based on v2.2.0 features, users will likely request:

1. **Email Integration** - "How do I send password reset links?"
2. **2FA/MFA** - "Can I enable two-factor authentication?"
3. **Notifications** - "Can I get alerts for security events?"
4. **Sharing** - "Can I share articles with other users?"
5. **Team Features** - "Can we have team workspaces?"
6. **Advanced Analytics** - "Can I get better insights from audit logs?"
7. **Password Expiration** - "Can we force password changes every 90 days?"

## 2. v2.3.0 Vision

### Theme: **"Communication & Collaboration"**

**Goal**: Transform WebScrape-TUI from a single-user security-focused tool into a collaborative platform with real-time communication and enhanced security features.

**Target Users**:
- Teams doing research together
- Organizations with compliance requirements
- Security-conscious users needing 2FA
- Users wanting to share curated content

## 3. Feature Proposals

### 3.1 Email & Notification System (HIGH PRIORITY)

**Rationale**: Password reset tokens exist but cannot be delivered. This is a critical gap.

**Features**:
- SMTP configuration (Gmail, SendGrid, custom)
- Email templates (password reset, welcome, security alerts)
- In-app notification system
- Email preferences per user
- Rate limiting for email sending
- Email delivery tracking (sent, delivered, failed)

**Use Cases**:
- Send password reset links via email
- Notify admins of security events
- Alert users of login from new location
- Send weekly summary reports
- Team collaboration notifications

**Technical Requirements**:
- SMTP library integration (`smtplib` or `aiosmtplib` for async)
- Email template engine (Jinja2)
- Database table: `email_queue`, `email_log`, `notification_preferences`
- Configuration via .env (SMTP_HOST, SMTP_PORT, etc.)
- Retry logic for failed emails

**Estimated Effort**: 3-4 sprints

---

### 3.2 Two-Factor Authentication (2FA/MFA) (HIGH PRIORITY)

**Rationale**: Essential for high-security environments and compliance requirements.

**Features**:
- TOTP (Time-based One-Time Password) via authenticator apps
- Backup codes (10 one-time use codes)
- SMS 2FA (optional, requires SMS provider)
- Email 2FA (fallback method)
- Per-user 2FA enforcement
- Admin-forced 2FA for specific roles
- Recovery process if device lost

**Use Cases**:
- User enables 2FA on their account
- Admin requires 2FA for all admin users
- User loses device, uses backup code
- Compliance requirement for HIPAA/SOC2

**Technical Requirements**:
- TOTP library (`pyotp`)
- QR code generation (`qrcode`)
- Database tables: `user_2fa_config`, `backup_codes`, `trusted_devices`
- SMS provider integration (Twilio) - optional
- Session management updates (trust device for 30 days)
- Recovery code generation and validation

**Estimated Effort**: 2-3 sprints

---

### 3.3 Password Expiration & Rotation (MEDIUM PRIORITY)

**Rationale**: Field exists in v2.2.0 but not enforced. Needed for compliance.

**Features**:
- Configurable password expiration (30/60/90/180 days)
- Force password change on next login
- Password history (prevent reuse of last 5 passwords)
- Expiration warnings (7 days before)
- Grace period after expiration (3 days)
- Per-role expiration policies

**Use Cases**:
- Company policy: passwords expire every 90 days
- User gets warning 7 days before expiration
- User attempts old password, system rejects
- Admin sets different policies for admins vs users

**Technical Requirements**:
- Database table: `password_history`
- Policy configuration system
- Login flow modification (check expiration)
- Email notifications (expiration warning)
- Cron job for expiration checks

**Estimated Effort**: 1-2 sprints

---

### 3.4 Article Sharing & Collaboration (MEDIUM PRIORITY)

**Rationale**: Users want to collaborate on research, share findings.

**Features**:
- Share articles with specific users
- Share collections/tags with teams
- Permission levels (view, comment, edit)
- Shared folders/workspaces
- Activity feed (user X shared article Y)
- Comments on shared articles
- Private vs shared articles toggle

**Use Cases**:
- Researcher shares article with colleague
- Team has shared workspace for project
- User adds comment to shared article
- Activity feed shows recent team actions

**Technical Requirements**:
- Database tables: `shared_articles`, `article_permissions`, `comments`, `activity_feed`
- Permission checking in all article operations
- New TUI screens for sharing management
- CLI commands for sharing
- API endpoints for collaboration

**Estimated Effort**: 3-4 sprints

---

### 3.5 Advanced Audit Log Analytics (LOW PRIORITY)

**Rationale**: Existing audit logs are underutilized. Add analytics layer.

**Features**:
- Security dashboard (failed logins, locked accounts)
- Anomaly detection (unusual login times/locations)
- User activity heatmaps
- Export audit logs (CSV, JSON)
- Scheduled audit reports (weekly/monthly)
- Compliance reports (HIPAA, SOC2 format)
- Real-time alerts (X failed logins in Y minutes)

**Use Cases**:
- Admin views security dashboard
- System detects login from new country, sends alert
- Generate compliance report for audit
- Export last 90 days of activity

**Technical Requirements**:
- Analytics engine (pandas for analysis)
- Dashboard visualization (matplotlib/plotly)
- Alert rule engine
- Report templates
- Scheduled task system

**Estimated Effort**: 2-3 sprints

---

### 3.6 Team & Organization Support (MEDIUM PRIORITY)

**Rationale**: Multi-tenant support for organizations with multiple teams.

**Features**:
- Organizations (parent entity)
- Teams within organizations
- Team-level quotas and permissions
- Organization admin role
- Team workspaces
- Cross-team sharing controls
- Organization-wide policies

**Use Cases**:
- Company creates organization "Acme Corp"
- Within Acme: Teams for Marketing, Research, Sales
- Marketing team has shared workspace
- Org admin sets company-wide password policy
- Teams can share articles within team only

**Technical Requirements**:
- Database tables: `organizations`, `teams`, `team_members`, `team_permissions`
- RBAC updates (org_admin, team_admin, team_member)
- Quota system updates (org-level + team-level)
- Hierarchical permission checking
- TUI/CLI updates for team management

**Estimated Effort**: 4-5 sprints

---

### 3.7 Enhanced Security Alerts (LOW PRIORITY)

**Rationale**: Proactive security monitoring and user awareness.

**Features**:
- Login from new location alert
- Login from new device alert
- Multiple failed login attempts alert
- Account locked notification
- Password changed confirmation
- New API key created alert
- Unusual activity detection

**Use Cases**:
- User logs in from new country, gets email
- Account locked after 5 failed attempts, admin notified
- User changes password, confirmation email sent
- Suspicious activity detected, admin alerted

**Technical Requirements**:
- Alert rule engine
- Email integration (depends on 3.1)
- Device fingerprinting
- IP geolocation (optional)
- Alert configuration per user

**Estimated Effort**: 1-2 sprints

## 7. Risk Assessment

### High Risks

**1. Email Deliverability** (Likelihood: Medium, Impact: High)
- **Risk**: Emails end up in spam, SMTP blocked
- **Mitigation**: Support multiple providers, SPF/DKIM guidance, testing checklist

**2. 2FA Adoption** (Likelihood: High, Impact: Medium)
- **Risk**: Users find 2FA too complex, disable it
- **Mitigation**: Excellent UX, clear instructions, backup codes, optional enforcement

**3. Password Expiration Frustration** (Likelihood: High, Impact: Medium)
- **Risk**: Users hate forced password changes
- **Mitigation**: Configurable policies, reasonable defaults (180 days), grace periods

### Medium Risks

**4. SMTP Configuration Complexity** (Likelihood: Medium, Impact: Medium)
- **Risk**: Users struggle with SMTP setup
- **Mitigation**: Presets for Gmail/Outlook, validation tool, clear error messages

**5. Migration Complexity** (Likelihood: Low, Impact: High)
- **Risk**: v2.2.0 → v2.3.0 migration fails
- **Mitigation**: Thorough testing, automatic backup, rollback procedure

### Low Risks

**6. Performance Degradation** (Likelihood: Low, Impact: Medium)
- **Risk**: Email queue processing slows system
- **Mitigation**: Async processing, rate limiting, monitoring

## 8. Technical Architecture Preview

### New Database Tables

```sql
-- Email & Notifications
CREATE TABLE email_queue (
    id INTEGER PRIMARY KEY,
    recipient TEXT NOT NULL,
    subject TEXT NOT NULL,
    body TEXT NOT NULL,
    template TEXT,
    variables TEXT,  -- JSON
    status TEXT DEFAULT 'pending',  -- pending, sent, failed
    attempts INTEGER DEFAULT 0,
    last_attempt TEXT,
    created_at TEXT NOT NULL,
    sent_at TEXT
);

CREATE TABLE email_log (
    id INTEGER PRIMARY KEY,
    email_queue_id INTEGER,
    status TEXT NOT NULL,  -- sent, delivered, bounced, failed
    error_message TEXT,
    created_at TEXT NOT NULL,
    FOREIGN KEY (email_queue_id) REFERENCES email_queue(id)
);

CREATE TABLE notifications (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    type TEXT NOT NULL,  -- security_alert, info, warning, error
    title TEXT NOT NULL,
    message TEXT NOT NULL,
    data TEXT,  -- JSON
    read INTEGER DEFAULT 0,
    created_at TEXT NOT NULL,
    read_at TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE notification_preferences (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL UNIQUE,
    email_enabled INTEGER DEFAULT 1,
    email_security_alerts INTEGER DEFAULT 1,
    email_password_reset INTEGER DEFAULT 1,
    email_weekly_summary INTEGER DEFAULT 0,
    inapp_enabled INTEGER DEFAULT 1,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- 2FA
CREATE TABLE user_2fa (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL UNIQUE,
    method TEXT NOT NULL,  -- totp, email
    secret TEXT NOT NULL,  -- Encrypted TOTP secret
    enabled INTEGER DEFAULT 0,
    verified INTEGER DEFAULT 0,
    created_at TEXT NOT NULL,
    verified_at TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE backup_codes (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    code TEXT NOT NULL,
    used INTEGER DEFAULT 0,
    used_at TEXT,
    created_at TEXT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE trusted_devices (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    device_fingerprint TEXT NOT NULL,
    device_name TEXT,
    ip_address TEXT,
    user_agent TEXT,
    trusted_until TEXT NOT NULL,
    created_at TEXT NOT NULL,
    last_used_at TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- Password History
CREATE TABLE password_history (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL,
    password_hash TEXT NOT NULL,
    created_at TEXT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- Security Alerts
CREATE TABLE security_alerts (
    id INTEGER PRIMARY KEY,
    user_id INTEGER,
    alert_type TEXT NOT NULL,
    severity TEXT NOT NULL,  -- low, medium, high, critical
    title TEXT NOT NULL,
    description TEXT NOT NULL,
    data TEXT,  -- JSON
    acknowledged INTEGER DEFAULT 0,
    acknowledged_at TEXT,
    acknowledged_by INTEGER,
    created_at TEXT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    FOREIGN KEY (acknowledged_by) REFERENCES users(id)
);
```
